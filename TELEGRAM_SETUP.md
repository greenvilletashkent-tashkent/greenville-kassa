# Telegram: подготовка тестовой версии

Модуль отключён по умолчанию. Для включения необходимы `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` и явное `TELEGRAM_ENABLED=1`. При включении требуется постоянное хранилище базы: очередь и расписание находятся в той же базе, что и продажи.

- `TELEGRAM_BOT_TOKEN`: токен бота, только в секретах окружения.
- `TELEGRAM_CHAT_ID`: ID группы для уведомлений и ежедневной сводки.
- `TELEGRAM_OWNER_IDS`: числовые ID руководителей через запятую; без списка личное меню отключено.
- `TELEGRAM_REPORTS_ENABLED=1`: включает только личные отчёты разрешённых руководителей, если `TELEGRAM_ENABLED` выключен; групповые уведомления и итог дня остаются выключены.
- `TELEGRAM_ENABLED=1`: включает обработку; `0` или отсутствие переменной отключает её, не удаляя очередь.
- `TELEGRAM_TEST_DIRECT=1`: при выключенном `TELEGRAM_ENABLED` разрешает администратору один прямой тест после подтверждения. Тест не изменяет базу и не повторяется автоматически. После теста удалить эту переменную и перезапустить сервер.

Добавьте бота в группу и предоставьте право отправлять сообщения. Руководитель должен открыть личный чат с ботом и отправить `/start`. Токены не храните в исходниках, тестах, коммитах и не отправляйте в чат. Для тестов используется локальная подмена Telegram API.

Меню работает через `getUpdates`: если настроен webhook, он конфликтует с этим способом получения сообщений. Команды из групп и запросы пользователей вне списка ID игнорируются. Сводка в группе содержит финансовые показатели, поэтому состав группы должен быть согласован владельцем.

Отчёт за день ограничен 21:00 по Asia/Tashkent. Календарь пропущенных отчётов сохраняется после включения модуля. При первом включении не восстанавливаются дни до его активации.

Если Telegram мог принять сообщение, но ответ потерялся, оно помечается «Требует проверки» и автоматически не повторяется. Администратор должен сверить чат и явно отметить доставку или разрешить повтор, который может создать дубль.

Существующие старые данные не всегда содержат достаточную историю для точной реконструкции состояния на прошлую дату. Там, где состояние долга или наличной кассы невозможно определить, результат должен оставаться неизвестным; финансовые отчёты на реальных данных перед внедрением требуют отдельной сверки.
